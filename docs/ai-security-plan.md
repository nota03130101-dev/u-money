# U Money AI 安全与隐私计划

## 1. 安全目标

第一版要保护四类内容：

- Supabase 用户身份和访问令牌；
- 模型 API 密钥；
- 用户账单、金额、类别和备注；
- AI 调用额度。

AI 功能失效时，现有记账功能仍然可用。

## 2. 密钥管理

### 可以出现在前端

- Supabase 项目公开地址；
- Supabase publishable key；
- AI 服务公开地址。

这些公开配置仍要受到 RLS、CORS、身份验证和限流保护。

### 只能出现在后端环境变量

- 模型 API 密钥；
- Supabase JWT 验证所需的后端秘密信息（如果当前项目确实需要）；
- 日志平台写入密钥；
- 部署平台内部凭据。

### 明确禁止

- 不使用 Supabase `service_role` 读取用户账单；
- 不把模型密钥写入 JavaScript、GitHub、CSV、日志或错误响应；
- 不在 `.env.example` 中填写真实值；
- 不通过聊天、截图或测试报告传播密钥。

如果密钥泄露，应立即在供应商后台停用并创建新密钥，而不是只从代码中删除。

## 3. 用户身份与数据隔离

所有 AI 接口（除 `/health`）必须验证 Supabase 访问令牌。

月度总结不查询 Supabase：

1. 前端在当前用户已经可见的记录中计算月度汇总；
2. 后端只验证 Bearer 令牌和汇总 JSON 的格式；
3. 后端不接受 `user_id`，也不接受完整账单；
4. AI 服务只把验证后的汇总数据转交给模型；
5. 普通云端记录仍由 Supabase RLS 隔离。

前端提供的 `user_id` 不可信，因此接口不包含该字段。

必须用两个虚构测试账号进行隔离测试：

- 账号 A 创建测试记录；
- 账号 B 请求同月份总结；
- B 的统计和总结中不能出现 A 的任何数据；
- 过期令牌、错误项目令牌和修改过的令牌都必须被拒绝。

## 4. 发送给模型的数据最小化

自然语言智能记账必须把用户输入发送给模型，因此界面应提示用户不要输入银行卡号、身份证号、密码等内容。

月度总结只发送：

- 月份；
- 总收入、总支出和余额变化；
- 记录数量；
- 各支出类别的合计和比例。

月度总结禁止向模型发送：

- 邮箱和用户编号；
- 每条账单；
- 日期明细；
- 完整备注；
- Supabase 访问令牌；
- 设备信息。

如果模型供应商支持不保留数据或零数据保留设置，部署前应启用，并核对供应商的数据处理条款。

## 5. Prompt 注入和模型误差

Prompt 注入是指用户在输入中加入“忽略原规则”等内容，试图改变模型行为。

第一版防护：

- 把用户文本明确标记为待解析数据，而不是系统指令；
- 模型没有数据库、网络和工具调用权限；
- 使用严格结构化输出；
- Pydantic 拒绝额外字段；
- 金额和日期经过业务验证；
- 解析结果必须由用户确认；
- 月度金额由 Python 计算，模型不能覆盖；
- 模型文字不得包含未经汇总数据支持的具体金额。

## 6. 调用次数限制

限流是限制一个用户在一段时间内可以调用多少次，防止误操作和费用失控。

第一版单实例建议：

- 每个用户每分钟最多 5 次 AI 请求；
- 智能解析每天最多 30 次；
- 月度总结每天最多 10 次；
- 单次自然语言最多 1000 个字符；
- 单次解析最多产生 20 条候选记录；
- 请求正文最大 8 KB。

最小实现可以使用 FastAPI 进程内存记录计数，不增加 Redis。它在服务重启后会清零，适合少量朋友试用，但不属于强计费控制。

同时必须在模型供应商后台设置：

- 每月消费上限；
- 用量告警；
- 只允许需要的模型或项目使用密钥。

如果以后需要稳定、跨实例的限流，再评估增加 Supabase 使用量表；第一版不修改现有数据库结构。

## 7. 日志规则

### 允许记录

- 随机生成的 `request_id`；
- 时间戳；
- 接口名称；
- HTTP 状态码；
- 请求耗时；
- 模型调用耗时；
- 模型名称或内部别名；
- Prompt 版本；
- 输入和输出 token 数量；
- 解析出的候选记录数量；
- 错误类别，例如超时、限流、格式验证失败；
- 用户编号经过带服务端秘密盐值的不可逆哈希后的结果。

哈希用户编号只用于判断同一用户的调用次数，不能用于恢复真实用户编号。

### 禁止记录

- Supabase access token、refresh token 和 Authorization 请求头；
- 模型 API 密钥和任何数据库密钥；
- 邮箱、密码、IP 与用户编号原文；
- 自然语言记账原文；
- 完整 Prompt；
- 模型原始请求和原始响应；
- 单条账单、金额、类别、备注和 CSV 内容；
- 月度收入、支出、余额和类别统计；
- 异常对象中可能包含的请求正文或请求头。

生产环境关闭详细调试日志。日志保留时间应尽量短，例如 14 至 30 天，并限制只有维护者可访问。

## 8. 错误、超时和重试

- 模型调用超时：15 秒；
- 整个请求超时：20 秒；
- 临时网络错误最多重试一次；
- 模型结构错误最多修复一次；
- 限流和输入错误不重试；
- 用户取消页面请求时，后端应尽量取消尚未完成的模型调用。

前端错误信息只告诉用户下一步，不暴露内部细节：

```text
智能解析暂时不可用，请稍后重试或使用手动记账。
```

后台日志只记录错误类别和 `request_id`，不记录输入内容。

## 9. 降级方案

| 故障 | 用户仍然可以做什么 | 页面提示 |
|---|---|---|
| AI 服务无法连接 | 手动添加、编辑、删除和筛选账单 | 智能功能暂时不可用 |
| 模型超时 | 使用手动表单 | 请求超时，请稍后重试 |
| 模型返回错误格式 | 修改原句或手动填写 | 无法可靠识别，请确认内容 |
| 月度总结失败 | 查看程序计算的月度统计和分类图表 | 文字总结暂时不可用 |
| Supabase 会话过期 | 本地功能仍可显示；云端 AI 功能暂停 | 请重新登录 |
| 达到调用限制 | 普通记账功能不受影响 | 今日智能功能次数已用完 |

AI 失败不能清空页面记录，也不能自动退出用户或覆盖已有账单。

## 10. CORS 与网络

正式环境只允许：

- U Money 的 GitHub Pages 正式网址；
- 明确需要的本地开发地址。

不使用允许所有来源的 `*` 配置。所有生产请求使用 HTTPS。

`/health` 可以公开访问，但只返回服务是否运行。其他路由必须验证身份。

## 11. 上线前安全测试

使用 pytest 和假的模型客户端检查：

- 无 Authorization 请求返回 401；
- 过期、篡改、错误签发者令牌返回 401；
- 账号 B 无法获取账号 A 的月度数据；
- 前端传入伪造 `user_id` 不起作用；
- 超长文本和过大请求被拒绝；
- 非法金额、日期和类型被拒绝；
- 模型返回非 JSON、缺字段或多字段被拒绝；
- 超时和限流返回统一错误；
- 无数据时不调用模型；
- AI 失败时不写入 Supabase；
- 测试捕获的日志中没有敏感字段。

使用真实模型前，只用虚构数据进行一次人工验收。不要把真实个人账单放入测试样例、截图、Issue 或提交记录。

## 12. 第一版可接受的剩余限制

- 进程内限流在服务重启后清零；
- 单实例暂时没有高可用；
- 月度总结是辅助文字，不是财务建议；
- 模型供应商仍会收到自然语言解析文本和月度汇总数据；
- 用户必须自行核对智能记账候选结果；
- 第一版不处理多个币种、共享账本或组织账号。

这些限制应在真正扩大用户范围前重新评估。
